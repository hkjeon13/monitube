# 분석 히트맵·성과표 정렬·빈출 키워드 UI 개선 계획

> 작성일: 2026-08-13
>
> 상태: 계획 수립 완료, 미구현
>
> 대상 화면: 분석 페이지의 `게시 요일·시간 성과`, `채널별 성과`, `키워드별 성과`, `반응이 큰 댓글`, 빈출 키워드 영역

## 1. 목적

분석 화면에서 다음 세 가지 사용성 문제를 개선한다.

1. 게시 시간 성과가 현재 6시간 단위로 묶여 있어 실제 게시 적정 시간을 세밀하게 비교하기 어렵다.
2. 채널별·키워드별 성과표의 각 컬럼에 오름차순과 내림차순 버튼이 동시에 노출되어 정렬 조작이 복잡해 보인다.
3. `영상 대본 빈출어`와 `댓글 빈출어`가 별도 패널로 나뉘어 화면 흐름이 끊기고, 두 패널을 직접 전환하며 비교할 수 없다.

이번 작업은 다음 결과를 목표로 한다.

- 게시 시간 성과를 3시간 단위의 8개 구간으로 제공한다.
- 셀 색의 진하기가 무엇을 의미하는지 항상 보이는 gradient 범례로 설명한다.
- 성과표의 각 컬럼에는 현재 방향을 나타내는 화살표 버튼 하나만 노출한다.
- 정렬 버튼은 기본 `▼` 상태에서 클릭할 때마다 `▲`와 `▼`로 전환한다.
- `영상 대본 빈출어`와 `댓글 빈출어`를 `자주 등장하는 키워드` 패널 하나로 통합한다.
- 통합 패널 안에 `영상`, `댓글` 탭을 두고 선택한 탭의 키워드 표를 표시한다.
- 통합 키워드 패널을 `반응이 큰 댓글` 패널과 같은 행에 배치한다.
- API 응답 구조는 유지하고 집계 단위와 UI 표현만 변경한다.

## 2. 확인된 현재 동작

### 2.1 게시 요일·시간 성과

- 시간 구간은 `00–06`, `06–12`, `12–18`, `18–00`의 4개다.
- Python 분석 경로는 게시 시각을 6시간 단위로 집계한다.
- Rust 분석 API도 SQL에서 게시 시각을 6시간 단위로 집계한다.
- 프런트엔드는 4개 시간 구간을 고정 배열로 렌더링한다.
- 셀의 진하기는 해당 셀의 `중앙 조회/일`을 현재 결과의 최댓값과 비교해 계산한다.
- 셀 툴팁에는 요일, 시작 시각, 영상 수, 중앙 조회/일이 표시되지만 색 농도 자체의 의미를 설명하는 범례는 없다.

### 2.2 채널별·키워드별 성과표

- `범위`, `영상`, `조회수`, `수집 댓글`, `최근 영상`의 5개 컬럼 모두 정렬 대상이다.
- 각 컬럼 헤더에 `▲`와 `▼` 버튼이 동시에 노출된다.
- 초기 프런트 정렬 상태는 `null`이며 API가 반환한 순서를 그대로 표시한다.
- API 기본 순서는 영상 수 내림차순, 조회수 내림차순, ID 순으로 정렬된다.
- 활성 정렬 방향은 버튼 색상과 `aria-sort`로 표시된다.

### 2.3 영상·댓글 빈출어

- `영상 대본 빈출어`와 `댓글 빈출어`는 같은 `KeywordFrequencyPanel`을 corpus별로 두 번 렌더링한다.
- 두 패널은 제목, 문서 수, 빈출어 목록, 제외 키워드 관리 메뉴를 각각 가진다.
- `반응이 큰 댓글`은 12컬럼 grid 중 8컬럼, 빈출어 패널은 각각 4컬럼을 차지한다.
- 개요 화면에서는 `반응이 큰 댓글 + 영상 대본 빈출어`가 한 행을 구성하고, `댓글 빈출어`는 다음 행의 4컬럼 패널로 남는다.
- 빈출어 결과는 현재 순위형 목록이며 키워드, 총 출현 횟수, 해당 키워드가 등장한 영상 또는 댓글 수를 제공한다.
- 제외 키워드 설정은 영상 대본과 댓글 corpus별로 별도 저장된다.

## 3. 목표 동작

### 3.1 3시간 단위 히트맵

시간 구간을 다음 8개로 고정한다.

| 버킷 값 | 화면 표시 |
| ---: | --- |
| 0 | `00–03` |
| 3 | `03–06` |
| 6 | `06–09` |
| 9 | `09–12` |
| 12 | `12–15` |
| 15 | `15–18` |
| 18 | `18–21` |
| 21 | `21–00` |

- 기준 시간대는 화면 문구와 동일하게 한국 시간(`Asia/Seoul`)으로 통일한다.
- 각 셀의 대표 값은 기존과 동일하게 해당 구간 영상들의 `중앙 조회/일`을 사용한다.
- 보조 값으로 해당 구간의 영상 수를 표시한다.
- 영상이 없는 구간은 값 없이 빈 셀로 표시하고 툴팁과 접근성 문구에 `영상 없음`을 제공한다.
- 기존 응답 필드 `weekday`, `hourBucket`, `videoCount`, `medianViewsPerDay`는 변경하지 않는다.

### 3.2 색 농도 범례

히트맵 위 또는 아래에 항상 보이는 gradient 범례를 배치한다.

```text
낮은 중앙 조회/일  [연한 주황 ───────── 진한 주황]  높은 중앙 조회/일
```

- 연한 색은 선택한 분석 결과 내에서 상대적으로 낮은 `중앙 조회/일`을 의미한다.
- 진한 색은 선택한 분석 결과 내에서 상대적으로 높은 `중앙 조회/일`을 의미한다.
- 범례 옆에 `색이 진할수록 해당 시간대의 중앙 조회/일이 높습니다.`라는 설명을 제공한다.
- 색만으로 정보를 전달하지 않도록 셀 내부 수치, 셀 `aria-label`, 툴팁을 함께 유지한다.
- 빈 셀의 배경은 성과가 낮다는 뜻으로 오해되지 않도록 gradient 범위와 구분되는 중립색으로 표시한다.
- 데이터의 최댓값이 0이거나 데이터가 없을 때도 0으로 나누거나 과도하게 진한 색이 나오지 않도록 안전한 기본값을 사용한다.

### 3.3 컬럼별 단일 정렬 화살표

각 컬럼에는 두 버튼이 아니라 화살표 버튼 하나만 표시한다.

| 상태 | 아이콘 | 정렬 의미 | 클릭 후 |
| --- | --- | --- | --- |
| 기본/내림차순 | `▼` | 큰 값 또는 최신 값부터 | `▲` 오름차순 |
| 오름차순 | `▲` | 작은 값 또는 오래된 값부터 | `▼` 내림차순 |

세부 동작은 다음과 같이 정의한다.

1. 화면 최초 진입 시 API의 기본 랭킹과 일치하도록 `영상` 컬럼을 활성 컬럼, 내림차순(`▼`)으로 둔다.
2. 모든 컬럼 헤더에는 현재 사용할 수 있는 방향 버튼 하나만 보이게 한다.
3. 활성 컬럼의 `▼`를 클릭하면 같은 컬럼을 오름차순으로 정렬하고 아이콘을 `▲`로 바꾼다.
4. 활성 컬럼의 `▲`를 다시 클릭하면 내림차순으로 정렬하고 아이콘을 `▼`로 바꾼다.
5. 비활성 컬럼을 클릭하면 해당 컬럼이 활성 정렬 기준이 된다. 비활성 컬럼의 최초 적용 방향은 내림차순(`▼`)으로 한다.
6. 새 컬럼이 활성화되면 이전 컬럼은 비활성 상태로 돌아가며, 실제 데이터 정렬에는 활성 컬럼 하나만 사용한다.
7. `범위`는 한글 자연 정렬을 사용하고, 숫자 컬럼은 숫자 비교를 사용하며, `최근 영상`은 날짜 비교를 사용한다.
8. 값이 `null`인 행은 오름차순·내림차순 모두 마지막에 유지한다.
9. 값이 같은 행은 기존 API 순서를 유지해 클릭할 때마다 행이 불필요하게 흔들리지 않게 한다.

아이콘의 시각 상태와 접근성 상태도 함께 맞춘다.

- 활성 헤더에만 강조색을 적용한다.
- `<th aria-sort="ascending|descending">`으로 현재 정렬 상태를 전달한다.
- 버튼의 `aria-label`은 다음 클릭의 동작을 설명한다. 예: `조회수 오름차순으로 정렬`, `조회수 내림차순으로 정렬`.
- 키보드 `Tab`으로 각 컬럼 버튼에 접근하고 `Enter` 또는 `Space`로 토글할 수 있어야 한다.
- 버튼 하나의 클릭 영역은 모바일에서도 누르기 쉬운 크기를 확보한다.

### 3.4 `자주 등장하는 키워드` 통합 패널

기존 `영상 대본 빈출어`, `댓글 빈출어` 제목을 제거하고 하나의 패널로 통합한다.

```text
┌────────────────────────────────────────────┬──────────────────────┐
│ 반응이 큰 댓글                             │ 자주 등장하는 키워드 │
│                                            │ [영상] [댓글]        │
│ 댓글 목록                                  │ 선택한 탭의 표       │
└────────────────────────────────────────────┴──────────────────────┘
```

- 패널 제목은 `자주 등장하는 키워드`로 고정한다.
- 제목 아래에 `영상`, `댓글` 순서의 탭을 배치한다.
- 기본 탭은 분석의 `개요`와 `영상` 화면에서는 `영상`, `댓글` 화면에서는 `댓글`로 한다.
- 탭을 전환해도 분석 페이지의 기간, 범위, 채널·키워드 필터는 그대로 유지한다.
- 탭 전환은 이미 응답에 포함된 `videoKeywords`, `commentKeywords`를 사용하며 추가 API 요청을 발생시키지 않는다.
- 현재 탭에 따라 인덱싱 문서 수와 빈 결과 문구를 바꾼다.
- 현재 목록 표현은 실제 표로 변경한다.

| 영상 탭 컬럼 | 의미 |
| --- | --- |
| 순위 | 현재 빈도 순위 |
| 키워드 | 영상 대본에서 추출된 단어 |
| 출현 횟수 | 선택 범위 내 전체 출현 횟수 |
| 영상 수 | 해당 키워드가 등장한 영상 수 |

| 댓글 탭 컬럼 | 의미 |
| --- | --- |
| 순위 | 현재 빈도 순위 |
| 키워드 | 댓글에서 추출된 단어 |
| 출현 횟수 | 선택 범위 내 전체 출현 횟수 |
| 댓글 수 | 해당 키워드가 등장한 댓글 수 |

- `제외 키워드 관리` 메뉴는 통합 패널에 하나만 둔다.
- 메뉴를 열면 현재 선택한 탭의 corpus를 대상으로 기존 제외 키워드 관리 dialog를 표시한다.
- 탭을 바꾸더라도 영상과 댓글의 제외 키워드 저장 영역은 서로 섞지 않는다.
- 저장이 끝나면 현재처럼 분석 데이터를 갱신하되 선택한 탭을 유지한다.
- 탭은 `role="tablist"`, 각 버튼은 `role="tab"`, 표 영역은 `role="tabpanel"`로 연결한다.
- 방향키로 탭을 전환하고, 활성 탭·포커스 상태가 시각적으로 구분되게 한다.

### 3.5 `반응이 큰 댓글`과 같은 행 배치

- `반응이 큰 댓글` 패널과 통합 `자주 등장하는 키워드` 패널을 같은 grid row에서 각각 8컬럼과 4컬럼으로 배치한다.
- 두 패널이 모두 표시되는 `개요`와 `댓글` 화면에서는 DOM 순서도 `반응이 큰 댓글 → 자주 등장하는 키워드`로 유지한다.
- `영상` 화면처럼 `반응이 큰 댓글`이 표시되지 않는 경우에는 키워드 패널을 12컬럼 너비로 확장해 불필요한 빈 공간을 만들지 않는다.
- 데스크톱에서는 두 패널의 상단선과 제목 영역을 맞추고, 내용이 긴 쪽 때문에 짧은 패널의 내부 요소가 과도하게 늘어나지 않게 한다.
- 태블릿·모바일 폭에서는 두 패널을 각각 12컬럼으로 세로 배치한다.

## 4. 구현 범위

### 4.1 Python 분석 집계

대상: `apps/api/monitube_api/analysis_insights.py`

- `hour // 6` 기반 버킷 계산을 `hour // 3` 기반으로 변경한다.
- 한국 시간으로 변환한 뒤 요일과 3시간 버킷을 계산하는 현재 순서를 유지한다.
- 0시, 3시, 21시와 자정 전후 경계 사례를 단위 테스트에 추가한다.

### 4.2 Rust 분석 API 집계

대상: `apps/api-rust/src/workspace_analysis.rs`

- SQL의 6시간 버킷 계산을 3시간 단위로 변경한다.
- `published_at`의 요일·시간 계산이 명시적으로 한국 시간 기준인지 확인하고 Python 결과와 일치하도록 맞춘다.
- API JSON 필드명과 타입은 유지한다.

### 4.3 히트맵 UI

대상: `apps/web/app/features/analysis/analysis-dashboard.tsx`

- 시간 배열을 `[0, 3, 6, 9, 12, 15, 18, 21]`로 변경한다.
- 끝 시각을 3시간 뒤로 계산해 8개 컬럼 라벨을 렌더링한다.
- 셀 툴팁에 `요일`, 전체 시간 범위, 영상 수, 중앙 조회/일을 표시한다.
- gradient 범례와 설명 문구를 히트맵에 추가한다.
- 셀별 `aria-label`을 추가해 색을 보지 않고도 같은 정보를 확인할 수 있게 한다.

### 4.4 정렬 UI와 상태

대상: `apps/web/app/features/analysis/analysis-dashboard.tsx`

- `SortableTableHeader`의 위·아래 두 버튼을 단일 토글 버튼으로 교체한다.
- 초기 상태를 `{ key: "videoCount", direction: "descending" }`으로 지정한다.
- 정렬 핸들러를 `컬럼 + 명시적 방향` 입력 방식에서 `컬럼 클릭에 따른 방향 전환` 방식으로 변경한다.
- 현재 활성 컬럼인지에 따라 같은 컬럼 토글과 새 컬럼 활성화를 구분한다.
- 문자열·숫자·날짜·`null` 비교 규칙을 명시적으로 유지한다.

### 4.5 스타일과 반응형 레이아웃

대상: `apps/web/app/styles/analysis.css`, 필요 시 `apps/web/app/styles/workbench-v2.css`

- 히트맵을 8열로 표시할 수 있는 최소 너비를 지정한다.
- 좁은 화면에서는 히트맵 표 부분만 가로 스크롤되게 하고 범례는 가능한 한 스크롤 밖에 유지한다.
- gradient bar, 낮음/높음 라벨, 빈 셀 표식의 스타일을 추가한다.
- 기존 2행 정렬 컨트롤 grid 스타일을 제거하고 단일 버튼 정렬 스타일로 교체한다.
- 활성 컬럼, hover, focus-visible 상태를 서로 구분한다.

### 4.6 키워드 패널 컴포넌트 통합

대상: `apps/web/app/features/analysis/keyword-frequency-panel.tsx`, `apps/web/app/features/analysis/analysis-dashboard.tsx`

- `KeywordFrequencyPanel`이 corpus 하나만 받는 구조를 영상·댓글 데이터 세트를 함께 받는 통합 패널 구조로 변경한다.
- 통합 컴포넌트가 활성 탭 상태와 탭별 인덱싱 문서 수를 관리한다.
- 대시보드에서 corpus별 컴포넌트 두 개를 렌더링하는 코드를 제거하고 통합 컴포넌트 하나만 렌더링한다.
- 키워드 순위 목록을 탭별 semantic table로 변경한다.
- 기존 제외 키워드 불러오기·추가·삭제·저장 로직에는 활성 corpus를 전달한다.
- dialog 제목과 설명은 활성 탭에 따라 `영상 대본 제외 키워드` 또는 `댓글 제외 키워드`로 유지한다.
- 탭 전환과 저장 후에도 불필요하게 dialog 상태나 다른 corpus 설정이 섞이지 않도록 상태 경계를 정리한다.

### 4.7 키워드 패널 레이아웃 및 스타일

대상: `apps/web/app/styles/analysis.css`, 필요 시 `apps/web/app/styles/workbench-v2.css`

- `analysis-panel-comments` 8컬럼과 통합 키워드 패널 4컬럼을 같은 행에 고정한다.
- 키워드 패널 단독 노출용 12컬럼 modifier를 추가한다.
- 탭 목록, 활성 탭, focus-visible, tabpanel, 키워드 표의 스타일을 추가한다.
- 4컬럼 폭에서도 표의 `키워드`가 우선 보이도록 숫자 컬럼 폭과 말줄임 규칙을 지정한다.
- 작은 화면에서는 표가 깨지지 않도록 최소 너비 또는 필요한 경우 패널 내부 가로 스크롤을 적용한다.

## 5. 테스트 및 검증 계획

### 5.1 집계 테스트

- `00:00`, `02:59`, `03:00`, `05:59`, `06:00`, `21:00`, `23:59`가 올바른 버킷에 포함되는지 확인한다.
- UTC 게시 시각이 한국 시간으로 변환되면서 날짜와 요일이 바뀌는 사례를 검증한다.
- Python과 Rust 경로가 동일한 입력에 같은 `weekday`와 `hourBucket`을 반환하는지 확인한다.
- 한 버킷에 짝수·홀수 개 영상이 있을 때 중앙값이 기존 정의와 동일한지 확인한다.

### 5.2 정렬 동작 테스트

각 컬럼에 대해 다음을 확인한다.

1. 최초 화면에서는 `영상` 컬럼이 내림차순(`▼`)이며 실제 행 순서도 일치한다.
2. 활성 `▼`를 클릭하면 오름차순과 `▲`로 바뀐다.
3. `▲`를 다시 클릭하면 내림차순과 `▼`로 돌아온다.
4. 다른 컬럼을 클릭하면 해당 컬럼이 내림차순 활성 기준이 된다.
5. 화면에는 컬럼당 화살표가 항상 하나만 존재한다.
6. 동률 행은 기존 순서를 유지한다.
7. `null` 값은 정렬 방향과 무관하게 마지막에 위치한다.
8. `aria-sort`, 버튼 `aria-label`, 키보드 조작이 시각 상태와 일치한다.

### 5.3 빌드 및 렌더링 검증

- Python 분석 API 관련 테스트를 실행한다.
- Rust API 테스트와 컴파일 검사를 실행한다.
- 웹 TypeScript typecheck와 production build를 실행한다.
- 데스크톱에서 8개 시간 구간, gradient 범례, 빈 셀, 툴팁을 확인한다.
- 모바일 폭에서 히트맵 가로 스크롤, 범례 가독성, 정렬 버튼 터치 영역을 확인한다.
- 채널별 성과와 키워드별 성과 양쪽에서 모든 정렬 컬럼을 실제로 토글한다.

### 5.4 통합 키워드 패널 테스트

- 화면에 `영상 대본 빈출어`, `댓글 빈출어` 패널이 각각 남지 않고 `자주 등장하는 키워드`가 한 번만 표시되는지 확인한다.
- `영상`, `댓글` 탭이 순서대로 노출되고 한 번에 하나만 활성화되는지 확인한다.
- 영상 탭에는 영상 대본 키워드와 영상 수, 댓글 탭에는 댓글 키워드와 댓글 수가 표시되는지 확인한다.
- 탭 전환이 추가 API 호출 없이 즉시 동작하는지 확인한다.
- 탭마다 빈 결과, 인덱싱 문서 수, 표 헤더가 올바르게 바뀌는지 확인한다.
- 제외 키워드 관리가 현재 활성 탭의 corpus만 불러오고 저장하는지 확인한다.
- 저장 후에도 활성 탭이 유지되고 갱신된 결과가 표시되는지 확인한다.
- 탭의 `aria-selected`, `aria-controls`, tabpanel 연결과 방향키·Tab 키 이동을 확인한다.
- 개요·댓글 화면에서 `반응이 큰 댓글`과 통합 키워드 패널이 같은 행에 있는지 확인한다.
- 영상 화면에서는 통합 키워드 패널이 전체 너비를 사용하는지 확인한다.
- 모바일에서는 두 패널이 올바른 순서로 세로 배치되고 표 내용에 접근할 수 있는지 확인한다.

## 6. 구현 순서

1. 현재 worktree와 관련 테스트 기준선을 재확인한다.
2. Python과 Rust의 시간대·버킷 계산을 3시간 단위로 통일한다.
3. 경계 시각과 한국 시간 요일 변환 테스트를 추가한다.
4. 프런트 히트맵을 8열로 변경한다.
5. gradient 범례, 빈 셀 설명, 접근성 문구를 추가한다.
6. 성과표 헤더를 단일 화살표 토글 방식으로 변경한다.
7. 정렬 상태·비교 규칙·접근성 속성을 검증한다.
8. 두 빈출어 패널을 `자주 등장하는 키워드` 탭 패널 하나로 통합한다.
9. 키워드 결과를 탭별 표로 변경하고 제외 키워드 관리의 corpus 경계를 유지한다.
10. 통합 키워드 패널을 `반응이 큰 댓글`과 같은 행에 배치하고 반응형 동작을 조정한다.
11. typecheck, API 테스트, Rust 검사, production build를 수행한다.
12. 실제 분석 화면을 데스크톱과 모바일 크기로 렌더링해 시각 검수한다.

## 7. 완료 기준

- 히트맵에 `00–03`부터 `21–00`까지 정확히 8개 시간 컬럼이 보인다.
- Python과 Rust 분석 경로 모두 3시간·한국 시간 기준으로 같은 데이터를 반환한다.
- 색이 진할수록 중앙 조회/일이 높다는 의미가 gradient와 문구로 명확히 보인다.
- 영상 없는 셀이 낮은 성과 셀과 시각적·문구상으로 구분된다.
- 성과표의 각 컬럼에는 화살표 버튼이 하나만 보인다.
- 기본 활성 정렬은 영상 수 내림차순 `▼`이다.
- 클릭할 때마다 같은 컬럼의 `▼ ↔ ▲`가 전환되고 실제 행 순서도 일치한다.
- 숫자, 한글, 날짜, `null`, 동률 행의 정렬 규칙이 안정적으로 동작한다.
- `영상 대본 빈출어`와 `댓글 빈출어`가 `자주 등장하는 키워드` 단일 패널로 통합된다.
- 통합 패널 아래의 `영상`, `댓글` 탭에서 각 데이터가 표 형식으로 정확히 전환된다.
- 제외 키워드 관리는 현재 탭의 영상·댓글 corpus를 서로 섞지 않는다.
- 데스크톱에서 `반응이 큰 댓글`과 `자주 등장하는 키워드`가 같은 행에 배치된다.
- `반응이 큰 댓글`이 없는 화면에서는 키워드 패널이 전체 너비를 사용한다.
- 모바일에서 정보가 잘리거나 정렬 버튼이 겹치지 않는다.
- 관련 테스트, typecheck, Rust 검사, production build가 모두 통과한다.
